#Архитектура приложения, структура проекта:


**Папка pages:** здесь хранятся папки всех основных страниц.
  Папка страницы: содержит главный файл (сам компонент страницы) и папку components
    В папке components находятся все компоненты, которые используются только на текущей страницы

**Папка general-components** здесь хранятся все переиспользуемые компоненты, общие на все приложение

**Папка layouts** содержит layout для приложения.

**Папка store** содержание папки будет дублировать содержание папки pages по названиям. Каждой странице page соответствует свой pinia-store для управления состояними. 

# ДАЛЬНЕЙШЕЕ МАСШТАБИРОВАНИЕ:

При появлении backend в store добавлется Map - карта, для которой переопределяются стандартные get и set  как функции, которые обновляют карту при каждом запросе и необходимости, возвращают данные странице.

При появлении backend, начинает фигурировать папка Service, которая является полным отражением API с адаптацией под фронтенд. Все имеющиеся endpoint - отдельный класс в сервисе. Который выполняет запрос и возвращает данные. 

## Логика работы с BACKEND снизу вверх: 
 Класс выполняет запрос к api. 
 
 Store создает экземпляр класса, создавая запрос, получая данные, обрабатывая их в нужном для страницы форматы и сохраняет в Map. 

 Страница вызывает запрос через store и получает уже нужные ей данные в необходимом формате.

 ## Обоснованность выбора архитектуры - разделение ответственности -> гибкость проекта
 
 Разделение запросов в папку service позволяет гибко подстраиваться фронтенду под изменение API. Страница и стор ничего не знают об АПИ

 ООП подход позволяет делать сервис запроса изолированным для каждого стора.

 Стор берет на себя всю обработку данных, преобразование их в нужный формат для страницы, здесь будут все адаптеры, вся необходимая логика

 Страница получает только необходимые ей данные
